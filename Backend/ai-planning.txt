AI travel planning

Set `GEMINI_API_KEY` in Backend/.env and configure Frontend's `VITE_API_URL` to the backend API URL. `GEMINI_MODEL` overrides the provider model. Without a key, the live backend still supplies deterministic itineraries and calculated estimates. Frontend demo mode retains the original basic spot planner.

POST /api/ai/plan accepts days (1–14), people (1–20), budget (total PKR), startDate (YYYY-MM-DD), region, departure, transport (own-car/public/rental), pace, interests, and instructions. The server validates AI-selected IDs, uniqueness and daily stop limits. Dates and cost arithmetic are server-owned. Only approved catalogue entries are retrieved.

Plans use a single base city because road travel times and visit durations are not in the current catalogue. Departure-city transfers, flights and entry fees are excluded. Lodging estimates use the lowest listed eligible hotel price, two people per room and all occupied nights checked against blackout dates; capacity and booking availability still need confirmation. Food and transport are explicitly labelled fixed planning assumptions, not supplier quotes. Refinements regenerate the itinerary using the form preferences. Natural-language requests do not override structured budget/date/group fields.

Ask Misty uses ranked keyword retrieval, with spot/tour/hotel links and save-to-trip controls for spots. It does not implement vector search or automatically book. Review summaries are cached for five minutes keyed by the normalized review content. Catalogue requests are coalesced and cached for one minute; approval/listing changes may take that long to appear.

Limits: 30 AI requests/hour per verified account (anonymous clients by IP), plus existing API limits. Provider calls have a 20-second timeout, maximum four concurrent calls and `AI_DAILY_CALL_LIMIT` (default 200) calls per process per rolling 24-hour window. The provider emits aggregate token counters to server logs without prompts or keys. These counters measure usage, not currency cost.

Caches and limits are in-memory and reset on restart. For multi-instance deployment, move these stores/counters to a shared service before treating them as a global spending ceiling. Model outages, invalid JSON, missing keys and exhausted provider limits fall back visibly. Catalogue outages return a retryable error.

Run `npm test` in Backend and `npm run build` in Frontend. Tests use a stubbed catalogue/provider and do not spend API credits.

Natural-language discovery: POST /api/ai/search accepts query (2–500 characters) and optional region. AI expands multilingual requests into English search synonyms; the server ranks only approved catalogue descriptions and returns literal matching terms. Explicit region wins over city names detected in the query. Search interpretations are cached for five minutes; results always use the current one-minute catalogue snapshot. No-match queries return an empty list. AI failures use keyword ranking. The UI labels limitations and never treats similarity as a probability. Accessibility, price, distance, exclusion and crowd requirements remain unverified. Demo mode retains browser embeddings and the region filter.

Weather-aware planning: the browser requests a 16-day Open-Meteo forecast for each base city in the plan, using CITY_COORDS and Asia/Karachi dates. Forecasts are cached in memory for 15 minutes, concurrent city requests coalesced, and fetches time out after 8 seconds. Missing/out-of-range dates are shown as unavailable. Heuristics flag rain probability >=60%, wind >=30 km/h, freezing minima, fog and precipitation codes; thunderstorms/heavy precipitation or wind >=50 km/h get a higher concern level. These are product planning rules, not official safety thresholds. The UI suggests same-city activity swaps only to a lower-concern day with fewer exposed outdoor activities (identified from catalogue text). Users apply swaps explicitly; dates, destinations and budget totals stay unchanged. Guide reports are unresolved records matched by city text and labelled as not independently verified. Forecasts do not verify route access, opening hours or individual mountain conditions.

Provider writing: POST /api/ai/draft requires a hotel or local guide JWT. Body: mode (description/translate/guest-reply/review-reply), language (en/ur), facts (name/city/location/description/amenities/activities/type strings), and source for translation/replies. Each fact and source is capped at 3,000 characters. Drafts are never cached or logged and the response is marked no-store. Missing AI, provider failure or invalid output returns 503 without changing existing content. The UI is in hotel listing add/edit and guide spot add/edit forms. Users review/edit generated text, apply it to the description field or copy replies; the endpoint never publishes, sends messages or writes listings. Normal save and approval workflows remain required. AI factual accuracy and translation quality still require human review.
